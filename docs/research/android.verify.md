## Additional findings
- SRC-VINTAGE: The researcher's AOSP line numbers come from the GitHub mirror aosp-mirror/platform_frameworks_base, which is archived and whose main ends at commit 1cdfff5 dated 2025-03-27 (checked with gh api). That is pre-Android 16. Android 17 source is public at android.googlesource.com/platform/frameworks/base, branch android17-release (last commit 94b4c163b7df, 2026-05-21) and tag android-17.0.0_r1. I downloaded those files to /var/tmp/sniper-research/src/aosp-android17-release/. The cited constants are the same in A17 r1, but the line numbers differ. A17 also adds code the 2025 copy lacks (the listener alarm API and its quota). No QPR1/QPR2 source tag exists yet, so QPR-only changes can only be checked against docs. Implication: cite android-17.0.0_r1 paths and lines.
- A17-LISTENER-QUOTA: In the Android 17 release, listener-based allow-while-idle alarms get their own relaxed quota. Evidence: build/release android17-release aconfig/cp2a/android.app/allow_alarms_with_relaxed_quota is ENABLED and READ_ONLY. AlarmManagerService A17 lines 2884-2890 set lowerQuota=false for directReceiver alarms when Flags.allowAlarmsWithRelaxedQuota() is on. Lines 2464-2467 and 2537-2540 then use ALLOW_WHILE_IDLE_LISTENER_QUOTA=72 over a 1-hour window (constants 782 and 786). Without the flag the old code would have downgraded them to the compat 7/hour quota. Implication: an FGS-held process can run 72 Doze-proof listener callbacks per hour with no exact-alarm permission.
- LISTENER-NO-ALLOWLIST: Listener alarms get no temporary power allowlist, so they grant no extra network or FGS-start rights. Evidence: AlarmManagerService A17 deliverLocked lines 5517-5555 deliver them by calling alarm.listener.doAlarm(this). The 10 s allowlist bundle is attached only on the PendingIntent path (getAlarmOperationBundle, lines 4811-4821). The system holds its alarm wake lock only until alarmComplete or LISTENER_TIMEOUT=5 s (line 758). Implication (inferred): in Doze, a listener callback has network only if the process is at or above BOUND_FOREGROUND_SERVICE (it runs an FGS) or the app is allowlisted.
- UNRESTRICTED-BG-NETWORK: Unrestricted battery also exempts the app from the Android 15+ background network block. Evidence: NetworkPolicyManagerService A17 updateRulesForBackgroundChainUL, lines 4994-5016, gives FIREWALL_RULE_ALLOW on FIREWALL_CHAIN_BACKGROUND to mPowerSaveTempWhitelistAppIds, mPowerSaveWhitelistAppIds and mPowerSaveWhitelistExceptIdleAppIds. The user allowlist feeds these sets (DeviceIdleController A17 lines 4516-4526). The chain is always enabled (line 1154). Implication: an Unrestricted app keeps network even while cached. Any app also gets network for the ~10 s temp-allowlist window after an exact-alarm PendingIntent fires.
- TOP-SLEEPING-NET: Showing an Activity is not enough to keep network with the screen off. When the screen turns off, the top app moves to PROCESS_STATE_TOP_SLEEPING, which equals BACKGROUND_THRESHOLD_STATE (NetworkPolicyManager A17 line 199; check at 860-866 is procState < TOP_SLEEPING). Its network is then cut after the background debounce: 5 s by default in A17, or 20 s if use_different_delays_for_background_chain is enabled. That flag is unset in the AOSP release configs (inferred: default off, but server-flippable). network_blocked_for_top_sleeping_and_above is ENABLED since bp1a (Android 16). Implication: an Activity-only sniper with the screen off loses network unless it runs an FGS, is Unrestricted, or is inside an alarm temp-allowlist window.
- CACHED-WAKELOCK: A wake lock cannot keep a cached app working. PowerManagerService A17 setWakeLockDisabledStateLocked, lines 4810-4822, disables any wake lock whose attributed UID is cached or frozen. Lines 4828-4832 (NO_CACHED_WAKE_LOCKS) disable partial wake locks for inactive UIDs above PROCESS_STATE_RECEIVER. Implication: the final countdown must run inside an FGS (or a visible Activity plus a wake lock), not a bare partial wake lock.
- FREEZER: Cached processes are frozen by the freezer after config_defaultFreezerDebounceTimeout=10000 ms (AOSP A17 config.xml line 7992, read in CachedAppOptimizer lines 671-673; Pixel overlays may differ). A frozen process runs no code. Its self-broadcasts wait until it is unfrozen (V5), and its exact listener alarms are dropped (AL8). Implication (inferred): the WebView renderer is bound with BIND_IMPORTANT and so inherits the app's cached state. Any in-page JS polling therefore stops about 10 s after the app leaves the foreground unless an FGS is running.
- NANOTIME-SLEEP: SystemClock docs say uptimeMillis 'is the basis for most interval timing such as Thread.sleep(long), Object.wait(long), and System.nanoTime()', and it stops in deep sleep. Implication (inferred): kotlinx.coroutines delay(), Handler.postDelayed and java.util.Timer do not advance while the CPU is suspended. Bid timing must come from *_WAKEUP alarms, or from code running under an FGS plus a partial wake lock that keeps the CPU awake through the last seconds.
- NONWAKEUP-DELAYED: Non-wakeup alarms are held while the screen is off. AlarmManagerService A17 line 795 sets DEFAULT_DELAY_NONWAKEUP_ALARMS_WHILE_SCREEN_OFF = true (DeviceConfig key at line 722). Implication: always use RTC_WAKEUP or ELAPSED_REALTIME_WAKEUP for snipe, monitor and end-of-auction alarms. setAlarmClock is RTC_WAKEUP by construction.
- ALARM-LIMITS: AlarmManagerService A17 line 759 sets DEFAULT_MAX_ALARMS_PER_UID = 500. setImpl (lines 2337-2346) throws IllegalStateException('Maximum limit of concurrent alarms 500 reached for uid ...') for non-system callers. Implication: reuse a request code per auction and cancel finished alarms. Never schedule one alarm per poll tick.
- ALLOW-WHILE-IDLE-COUNTING: The allow-while-idle quota only counts deliveries made while the device is in Doze or Battery Saver (AlarmManagerService A17 deliverLocked lines 5570-5590, 'if (doze || batterySaver)'). Outside those modes, back-to-back setExactAndAllowWhileIdle alarms are not quota-limited (inferred: only the bucket and app-standby rules apply, and exact allow-while-idle alarms are exempt from app standby).
- FGS-TEMP-ALLOWLIST-SCOPE: Any exact PendingIntent alarm from a permission holder targeting S+ gets the FGS-capable 10 s temp allowlist, including plain setExact() (AlarmManagerService A17 lines 2895-2897, mOptsWithFgs). Inexact setAndAllowWhileIdle gets mOptsWithoutFgs (TEMPORARY_ALLOWLIST_TYPE_FOREGROUND_SERVICE_NOT_ALLOWED with REASON_DENIED, lines 937-938). Implication: an inexact allow-while-idle monitor alarm cannot start an FGS from the background.
- SAMPLE-API-LEVELS: The Live Update API levels per developer.android.com references (fetched 2026-11-04) are as follows. Notification.ProgressStyle, setShortCriticalText, FLAG_PROMOTED_ONGOING, hasPromotableCharacteristics and canPostPromotedNotifications are API 36. setRequestPromotedOngoing, EXTRA_REQUEST_PROMOTED_ONGOING and POST_PROMOTED_NOTIFICATIONS are 'Added in version 36.1'. Notification.MetricStyle is 'Added in API level 37' (api_metric_style ENABLED in the cp2a release config). canUseFullScreenIntent is API 34. Implication: on the Pixel 9a (API 37) all are available; on older devices gate by Build.VERSION.SDK_INT_FULL >= VERSION_CODES_FULL.BAKLAVA_1.
- PROMOTED-APPOP-RISK: AppOpsManager A17 lines 3623-3626 declare OP_POST_PROMOTED_NOTIFICATIONS with default mode MODE_ERRORED. NotificationManagerService A17 (lines ~9876-9893) promotes only if checkPermissionForDataDelivery(POST_PROMOTED_NOTIFICATIONS) passes. User changes go through setCanBePromoted, which writes MODE_ALLOWED or MODE_IGNORED (lines 5097-5125). I did not find what flips the default for a freshly sideloaded app (unverified). Implication: call NotificationManager.canPostPromotedNotifications() at runtime and, if false, send the user to Settings.ACTION_MANAGE_APP_PROMOTED_NOTIFICATIONS.
- LIVE-UPDATE-CRITERIA: The live-update doc (fetched 2026-11-04) sets usage rules. A Live Update must be 'ongoing, user-initiated, and time-sensitive'. Ads, promotions, chat messages, alerts and upcoming calendar events are listed as inappropriate. 'events that are about to start can use a Live Update'. 'If the user explicitly indicates that they want to begin monitoring a background event ... you should also include an Unpin action'. 'Don't repost Live Updates that the user dismissed. Use setDeleteIntent to detect dismissed updates.' 'OEMs can enforce additional criteria.' Implication: start the promoted countdown only for the user-armed snipe, shortly before the end. Add an Unpin action, and honour dismissal with setDeleteIntent.
- AUDIO-RULES: Do not have the app play its own alert audio. Android 15 (behavior-changes-15): apps targeting 35 must be the top app or run an FGS to request audio focus, else AUDIOFOCUS_REQUEST_FAILED. Android 17 (behavior-changes-all) makes background playback and volume calls fail silently for all apps. For target 37 the app also needs an FGS with while-in-use capability, or the exact-alarm permission plus USAGE_ALARM. Beta 4 notes mention 'exempting alarm audio'. Implication: use notification channel sounds, which the system plays, for outbid/won/lost alerts.
- EBAY-SIGNIN-IN-WEBVIEW: Combining SI1-SI3 (inferred), only eBay's own username/password plus its 2FA can work in the app's WebView. Google sign-in fails with disallowed_useragent (since Sept 30, 2021) and Facebook Login stopped Oct 5, 2021. Passkeys need WEB_AUTHENTICATION_SUPPORT_FOR_APP with a Digital Asset Links association to a site the app owns (impossible for ebay.co.uk), or FOR_BROWSER, which is reserved for privileged browsers. Implication: the onboarding UI should say so, and offer a 'set an eBay password' path if the user normally uses Google or passkey sign-in.
- WM-ANDROID15-FIX: WorkManager 2.12.0-alpha01 'Fixed an issue where background network requests could fail on Android 15'. 2.11.1 'Fix network state constraint from passing while connectivity is blocked on Android 15 and above' (androidx work release notes, fetched 2026-11-04). Implication: if WorkManager is used for gentle monitoring, depend on 2.12.0 (stable Sept 23, 2026, minSdk 24) or at least 2.11.1.
- SYSTEMEXEMPTED-DOZE-ALLOWLIST: The AOSP A17 ServiceInfo javadoc for FOREGROUND_SERVICE_TYPE_SYSTEM_EXEMPTED (lines 423-449) lists both 'App is on Doze allowlist' and 'Apps holding SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM'. Whether the user power allowlist (Unrestricted) alone passes the custom checker SystemExemptedFgsTypePermission (ActiveServices A17 lines 3045-3093, which includes REASON_SYSTEM_ALLOW_LISTED) was not verified (inferred possibility). The safe path is USE_EXACT_ALARM plus FOREGROUND_SERVICE_SYSTEM_EXEMPTED.
- SERVER-FLIPPABLE-FLAGS: Several A17 behaviours depend on aconfig flags that have no value in the AOSP android17-release configs (cp2a, cp1a, bp1a-bp4a). Examples are com.android.server.net use_different_delays_for_background_chain and com.android.server.deviceidle disable_wakelocks_in_light_idle; the latter, if enabled, would also block background wake locks in light Doze (PowerManagerService A17 line 4775). Inferred: such flags default to DISABLED but are READ_WRITE, so Google can enable them server-side on Pixels. Implication: verify on the real Pixel 9a with 'adb shell dumpsys netpolicy', 'dumpsys power' and 'dumpsys alarm' rather than trusting AOSP defaults.
- DEV-VERIFICATION-INSTALL-PATH: The developer-verification FAQ says ADB installs never need verification and the 24-hour advanced-flow wait does not apply to ADB. Unregistered apps can be installed or updated only with the advanced flow enabled or via ADB. A free limited distribution account (up to 20 devices, no ID) can register the package instead. Implication: in the UK in 2027, the user can keep sideloading by ADB, enable the advanced flow once, or register the package name under a limited distribution account.
- CHROMIUM-BIND-IMPORTANT: Current chromium/chromium main (gh code search, 2026-11-04) shows base/android/java/src/org/chromium/base/process_launcher/LegacyChildServiceConnectionController.java and RebindingChildServiceConnectionController.java adding Context.BIND_IMPORTANT for the strong binding. - SIDELOADED-EXACT-ALARM-CHOICE: For a sideloaded app targeting 33+, USE_EXACT_ALARM is auto-granted and not revocable by the user (alarms guide), and it pins the app to the WORKING_SET bucket or better (AOSP A17 manifest line 6908 and shouldGetBucketElevation lines 2707-2712). Revoking SCHEDULE_EXACT_ALARM kills the app and deletes its exact alarms (AL2). The Play policy restricting USE_EXACT_ALARM does not apply outside Play (inferred). Implication: declare USE_EXACT_ALARM, not SCHEDULE_EXACT_ALARM.
